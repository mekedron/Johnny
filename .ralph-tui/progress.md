## Codebase Patterns (Study These First)

- **Run pytest in the worker container** (not api): the api image is built from production-shape Dockerfile (`COPY . .`) and has no bind mount unless launched via `./run-dev.sh`. The `worker` service in dev mode bind-mounts `./backend` to `/workspace`, so host edits are visible immediately. The image's `/opt/venv` was built via `uv` and has no `pip`; install dev deps with `uv pip install --python /opt/venv/bin/python pytest pytest-asyncio aiosqlite ruff mypy types-PyYAML`, then run `docker compose exec -w /workspace worker python -m pytest …`.
- **`PipelineConfig` is `@dataclass(frozen=True, slots=True)`**: add fields with sensible defaults so existing call-sites keep working without modification. Document the *why* in a docstring directly under the field — the file is the canonical config reference for the whole pipeline.
- **Barge-in has two paths**: fast VAD-driven (Johnny-ze3, in `_utterances`) cuts TTS within ~200 ms of speech onset; slow classifier (Johnny-di9, in `_classify_barge_in_intent`) runs post-utterance as a fire-and-forget task spawned at `_transcribe_and_emit`. The slow path is observability + edge-cases, not the user-facing budget — fail-open is the right default when its LLM is slow.
- **STT silence hallucinations belong at the adapter, not the pipeline gate**: Whisper segments expose `no_speech_prob` — the model's own probability that the audio was silence. Filtering on that signal inside `app/providers/faster_whisper_stt.py` catches *novel* hallucinations ("Does Olam A.P.I.", Welsh nonsense) that a curated stoplist in `pipeline.py` can never anticipate. The pipeline's `DEFAULT_NOISE_STOPLIST` (Johnny-ckz.14) handles known patterns ("you", "thank you", filler tokens); the adapter's `no_speech_threshold` handles everything else. Defence in depth — keep both.
- **Provider adapters live in the api image, not just meet-worker**: the in-process `BrowserPipelineSpec` (`app/services/browser_pipeline_runner.py`) means `/playground` runs the FULL voice pipeline inside the api container — so any STT-adapter change has to land in BOTH images (api + meet-worker). The api image is COPY-baked (`Dockerfile`), so after editing `app/providers/*.py` run `docker compose build api && docker compose up -d api` before exercising the playground; the worker has a bind mount and picks up host edits live, but the api does not.
- **`provider_credentials.is_active` per kind is touched in only two places**: (1) `app/api/providers.py` — `activate_provider` (deactivates same-kind siblings then flips this row True), `deactivate_provider` (explicit user click), `create_provider` (always inserts inactive). `update_provider` does NOT touch `is_active` — schema-driven merges drop the field via `merged = {k: v for k, v in baseline.items() if schema.field(k) is not None}` because the schemas don't declare `is_active`. (2) `app/services/providers_seed.py` — only mutates when `JOHNNY_PROVIDERS_FILE` exists. Missing file = early return = no-op. INSERT_ONLY mode skips existing rows entirely so `is_active` is preserved across restart. OVERWRITE mode is the only path that intentionally clears the flag (when the file explicitly lists `is_active: false` for an existing identity, per the documented export→edit→import roundtrip). Symmetric across LLM/STT/TTS — no kind-specific branch anywhere.
- **`ProviderSchema.tips` is the in-UI knowledge-capture surface**: when you need to put operator know-how (latency rules of thumb, knob trade-offs, cost guidance) directly inside `/providers`, edit the adapter's `field_schema()` and pass `tips=(ProviderTip(topic=..., body=...), ...)`. The schema serialises tips automatically; the frontend renders them as a "Latency & tuning tips" section below the form fields. Topic is a short headline; body is 1-2 sentences with a concrete number where possible. Adapter file is the canonical home — don't fork knowledge into a separate docs file (it goes stale next to the knobs it's about). After editing, rebuild the api image (`docker compose build api && docker compose up -d api`) — the COPY-baked Dockerfile won't pick up the change otherwise.
- **`_utterance_count` is NOT a valid turn_id from inside the response loop**: transcription (`_transcribe_and_emit`) and response (`_respond_to_transcript`) run as concurrent tasks (Johnny-har). By the time the response loop dequeues transcript N and starts router/answer/tts, the transcribe loop may have incremented `_utterance_count` past N. For activity-log-style cross-stage correlation (Johnny-ckz.7), stamp `(turn_id, anchor_ms)` in a `dict[int, tuple[int, int]]` keyed by `id(transcript)` at STT-finalise time, then `pop()` it when the response loop dequeues. Falls back to `_utterance_count + now` for transcripts injected via `feed_text` (no transcribe-loop stamp). Same caveat applies to ANY new code that needs "what turn am I in?" from the response side — don't read `_utterance_count` there.
- **The pipeline event bus is multiplexed**: every new event TYPE shares one Redis pub/sub channel per session and one `InMemoryEventBus.snapshot()` in tests. When adding a new type (e.g. Johnny-ckz.7's `PipelineTiming`), the existing tests that assert `[e.type for e in bus.snapshot()] == [...]` will fail because the new events leak in. The repo convention: filter at the test site — `[e.type for e in bus.snapshot() if e.type != "<new_type>"]` — rather than gating the publish at the source. Observability events (timings, traces) should publish unconditionally so they show up in the activity log; only the assertion list needs updating.
- **The migrate sidecar image must be rebuilt alongside api+worker**: `docker-compose.yml` defines `api`, `worker`, and `migrate` as three separate services with three separate images, all built from the same `backend/Dockerfile`. `docker compose build api` only rebuilds the api image — migrate keeps its old layer with whichever migrations it had at last build. After adding a new alembic revision, run `docker compose build api migrate worker` (or `docker compose build` for all) so the migrate sidecar can find your new `0008_*.py` file at startup. Symptom of missing this: migrate fails with `Can't locate revision identified by 'NNNN'` even though the file exists on the host and the api image has it.

  - For the in-UI tips, "concrete number wins over qualitative description" — "~150 ms time-to-first-audio on a modern CPU" is actionable, "fast" is not. Where I had no measured number I named the upstream documented benchmark or said "tracked separately" rather than fudging.
  - When inserting multi-line tabbed HTML into a Svelte file the Edit tool kept failing to match tabs. Falling back to a Python `read/replace/write` block preserves whitespace correctly and is much less brittle than trying to land long multi-line `Edit` calls — keep this trick in mind for any svelte/tsx file that uses tab indentation.
  - The Piper `chunk_bytes` field originally had no `help_text`. Both useful — field-level docs answer "what does this do", tips answer "what should I set it to and why".
