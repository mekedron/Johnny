## Codebase Patterns (Study These First)

- **Task lifecycle events are ephemeral; the row is the record (trt.25)**: all four task events (`task_queued|task_progress|task_completed|task_result_expired`) follow one contract — whoever settles the task OWNS the `agent_tasks` row (in-process coordinator resolver today, trt.24 worker later) and announces AFTER the row write (row-before-event, the trt.18 row-before-ack discipline applied to every announce); the status subscriber routes them via an early `return False` BEFORE `session_scope()` (`TASK_EVENT_TYPES` — never a DB write, chatty progress costs nothing), and `/ws/sessions/{id}` fans them out by pure payload passthrough (no WIRE_TYPE_MAP entry). Announce seams on the coordinator are constructor-wired through `build_task_coordinator` (publish_queued/publish_completed; contained, best-effort) vs post-construction attach for gate-owned seams (report_failed — needs say()). `TaskCompleted.status` is `done|failed` ONLY (drift-guarded ≡ `EXECUTOR_RESULT_STATUSES`); cancelled/expired announce nothing. A fast executor settles mid-ack: task_completed can arrive BEFORE turn_terminal in the frame stream.
- **Real-redis → real-WS integration tests (trt.25)**: `TestClient(app)` + the DEFAULT stream factory exercises the production `RedisEventStream` against compose redis (`tests/integration/test_task_events_ws.py`; loud-skip off-stack per the trt.35 pattern). `ws.receive_json()` can't time out — receive in a daemon thread, republish the identical event every ~200 ms through the real `RedisEventBus` (pub/sub subscribe race is unobservable, duplicates are harmless — assert on the first frame), bound the loop with a deadline; the TestClient context exit closes the WS and frees a stuck receiver.
