## Codebase Patterns (Study These First)

### Per-session provider + mode resolution (the real seam)
- **Production provider resolution is `build_provider_payload` (`backend/app/services/provider_payload.py:46-81`)**, which reads every `provider_credentials` row where `is_active IS TRUE`. `load_active_providers` (`backend/app/providers/loader.py:42`) is **dead in production** — it appears only in tests + docstrings. Don't be misled by docstrings that name it.
- Live callsites of `build_provider_payload`: `browser_sessions.py:518` (`_build_spec_from_event`), `:603` (`_build_spec_playground`), `session_scheduler.py:388` (scheduled meet-worker launch). Per-session overrides are layered by `_resolve_provider_overrides` (`browser_sessions.py:429-486`) **without mutating DB rows**.
- The **meet-worker is DB-free**: the API serialises the resolved payload into `JOHNNY_PROVIDER_CONFIG` env and the worker rebuilds via `ProviderRegistry.instantiate`. So any per-session provider override MUST be applied API-side before serialisation, never inside the worker.
- Mode resolution: event `payload.mode or meeting.mode or "free_auto_speak"` (`browser_sessions.py:529-533`); playground `payload.mode or BotMode.FREE_AUTO_SPEAK.value` (`:598`). **`meeting_configs.mode` is NOT NULL** (`models.py:288`) — a real meeting always has a mode. There is no global "default mode" row.

- ### Personality resolution layer (Johnny-oly.3)
- **`app/services/personality_resolver.py` is the personality seam**: `apply_personality(session, base_payload, personality, *, crypto)` sits **between** `build_provider_payload` (global active) and `_resolve_provider_overrides` (explicit request override). Returns `PersonalityResolution{payload, personality_id, personality_name, default_mode, fallbacks}` — never mutates `base_payload`. `select_personality(session, *, requested_id, meeting)` does the §4a precedence: request id → `meeting.personality_id` → the `is_default` row → None.
- **Override applies only when the FK row exists + `is_active=true` + decrypts**; else fall back to global-active for that kind + log `personality.fallback: kind=… personality_id=… provider_id=… reason=<missing|deactivated|undecryptable>`. **NULL FK = silent inherit** (don't log it — bootstrap "Johnny" has NULL FKs and would flood the log / defeat alert-filtering). Because of one-active-per-kind, a *valid* v1 override == global active, so the v1 payload effect is effectively nil; the live effects are playground `default_mode` seeding + fallback diagnostics + the `playground_overrides` decoration (`personality_id`/`name`/`fallbacks`) the .5 UI chip reads.
- **Wire it at every `build_provider_payload` callsite, API-side, before serialisation** (meet-worker is DB-free): browser builders via the guarded `_resolve_personality` (`browser_sessions.py`), scheduler inline (`session_scheduler.py`). Always wrap in try/except → degrade to global-active: personality resolution must never hard-fail a session (PRD §4a step 4), and stripped test schemas / missing `FERNET_KEY` must not break a start. **Mode**: only the *playground* seeds from `personality.default_mode`; a calendar meeting's NOT-NULL `meeting.mode` wins (PRD §4c) — don't seed it from the personality at session start.
- **Migration `ALTER ADD COLUMN` with an FK** (e.g. `0015` `meeting_configs.personality_id`): use an **inline column-level** `sa.ForeignKey(...)` inside `op.add_column` (no separate `ADD CONSTRAINT`) so the one statement runs on Postgres AND the SQLite migration-test harness (SQLite allows ADD COLUMN ... REFERENCES only for a nullable column). Guard with a column-exists check for idempotency. SQLite-create_all unit tests get the column from the model; validate the real DDL + drift on isolated Postgres (`johnny_mig_test`) — a SQLite `test_migration_*` is blocked here because the model is already ahead of the migration (create_all would pre-add the column, no-op'ing the guard).

### Schema / migration conventions
- Integer autoincrement PKs everywhere (no UUIDs). `TimestampMixin` (`models.py:130-143`) for `created_at/updated_at`.
- Enums: `enum.StrEnum` + `SAEnum(..., native_enum=False, length=N, values_callable=_str_enum_values)` (`models.py:112-127`). Migrations store them as VARCHAR + CHECK via the `_in_list()` helper (see `0009_pipeline_settings.py`), never native PG enums (keeps SQLite tests working).
- Singleton / single-active rows use a **partial unique index** (`0002_provider_active_unique.py:21-27`; `models.py:537-543`): `Index(name, col, unique=True, postgresql_where=text(...), sqlite_where=text(...))`.
- Bootstrap seed inside the migration via `op.execute("INSERT ... WHERE NOT EXISTS ...")` (idempotent), as `0009` does for `pipeline_settings`. Migrations run at boot (`app/db/bootstrap.py:bootstrap`, called from `main.py:48` lifespan) BEFORE `seed_providers_from_file` (`main.py:62-65`).
- Boot-time drift guard `check_model_db_drift` (`bootstrap.py:78-106`) aborts if an ORM model has no matching migration — model + migration must land together.
