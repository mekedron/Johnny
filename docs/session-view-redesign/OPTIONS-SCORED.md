# Architecture Options, Adversarially Scored — Session-View Re-Imagining

**Status:** Options analysis · **Created:** 2026-06-15 · **Author:** second (parallel) investigation agent.
**Companions:** [`RED-TEAM-REVIEW.md`](./RED-TEAM-REVIEW.md) · [`SESSION-WORKSTREAMS-PRD.codex.md`](./SESSION-WORKSTREAMS-PRD.codex.md) · [`DESIGN.md`](./DESIGN.md) · unified [`PRD.md`](./PRD.md).

> **Method.** Four architecture proposals were generated by **four independent agents**, each championing a
> different philosophy and each reading the real code (`backend/johnny/agent/*`, `events.py`, `models.py`, the
> frontend assembly layer) before proposing. They were then scored by a **3-judge panel** (product / staff-eng /
> shipping lenses) on five axes, and a synthesis was produced. This complements the parallel agent's Options A–D
> (PRD §8) / Directions A–C (DESIGN §9), which were not independently scored.
>
> These four options (**P1–P4**) are framed around the **async/behaviour axis** the operator cares about, and —
> importantly — **they stack** rather than compete (see §"Recommended synthesis").

---

## 0. What all four proposals agreed on (the convergent core)

Independently, every proposal landed on the same two load-bearing conclusions. Treat these as settled:

1. **The fix is to make the inline answer-loop a first-class task.** Today there are two execution paths —
   router-`delegate` tasks (tracked: `agent_tasks` + `TaskCoordinator` registry + `status_summary()`) and the
   **inline native tool loop** inside `llm_node` (untracked, synchronous, invisible to status). The unification is
   to route the inline loop through the *same* `agent_tasks`/registry machinery so any non-trivial work is one
   observable, status-queryable object. This is the direct fix for session 3's "I don't have any tasks in flight."

2. **There is a hard ceiling on true parallelism, and it is honest to name it.** LiveKit's
   `on_user_turn_completed` hook is **await-chained** (`backend/johnny/agent/gate.py` documents this) — the router
   and SDK process **one turn at a time**, and the STT layer emits **one `ChatMessage` per detected
   end-of-utterance**. So a `request_id`/`thread_id` does **not** buy true audio-level concurrent routing of two
   people talking at once. What it *does* buy: correlating **overlapping work and out-of-band deliveries** to the
   request they belong to, and telling apart interleaved asks **across turns**. The operator's "parallel" pain is
   real, but its tractable form is *correlation + off-turn work + clear delivery attribution*, **not** simultaneous
   dual-routing. (This is a sharper statement of the ceiling than the PRD/DESIGN make.)

Everything below differs only in **how far past those two points** to go.

## 1. The four options

### P1 — Incremental, UI-first (reuse `turn_id`; promote inline work at the observability layer)

- **Thesis.** Split the frontend monolith (`buildDecisionEntries`) into three independent read-models over data we
  **already persist** (`agent_decisions`→Router, `agent_utterances`→Delivery,
  `agent_tasks`+`agent_tool_calls`+`agent_model_calls`→Tasks); wire the dropped `task_*` WS events; and close the
  split-brain by having the inline loop emit a lightweight **`work_unit`** `agent_tasks` row. **No `request_id`.**
- **Correlation.** Keep `turn_id` (`gate.py:TurnIndex.resolve`) as the only key.
- **Task model.** Make the inline half use the existing `agent_tasks`/`TaskCoordinator`; `begin_observed()` seeds
  the registry **without** a worker wake-ping; gate creation on `native_tools_active ∧ ≥1 tool step` so cheap reply
  turns create nothing (preserves replay parity for non-tool turns).
- **Proactive delivery.** None new — a `work_unit`'s result *is* the turn's spoken reply.
- **Phases.** P0 3-panel split *(M, closes `Johnny-trt.33`)* → P1 inline→`work_unit` *(L)* → P2 approximate
  request-group badge *(S)* → P3 request-scope barge-in partials *(S)*.
- **INV-1/INV-2.** Unchanged (a `work_unit` is an `agent_tasks` row, never a `TurnTerminal`).
- **Cannot do.** No true parallel-request disambiguation — `turn_id` is linear, so "is ask B about ask A's
  in-flight work?" stays heuristic.
- **Risks.** `work_unit` double-execution if the worker claim doesn't exclude `answer.*` kinds; `agent_tasks`
  bloat without the tool-step gate; refetch storm from many `TaskProgress` (the existing 800 ms debounce coalesces).

### P2 — `request_id` correlation backbone

- **Thesis.** Mint a durable **`request_id`** and thread it through every event + row as a correlation field
  **parallel to** `turn_id`; bucket the three panels by it; attribute out-of-band deliveries + inline work to their
  originating request.
- **Correlation.** `request_id == turn_id` for a fresh utterance in v1 (minted 1:1), but it is a **durable,
  cross-turn, turn-independent** handle (mintable without a turn; supports later follow-up/split-ask).
- **Task model.** Heal the split-brain by making the registry span inline work (`begin_inline()` settles on the
  reply done-callback).
- **Proactive delivery.** Already exists end-to-end (`TaskSpeechDeliverer`); P2 only adds **request attribution**.
- **Phases.** P0 id backbone *(L, no behaviour change)* → P1 heal split-brain (registry spans inline) *(M)* → P2
  delivery attribution *(M)* → P3 frontend request bucketing + Panel C *(L, `Johnny-trt.33`)* → P4 parallel-ask
  correlation hardening *(M)*.
- **INV-1/INV-2.** Preserved (`turn_id` stays the `TurnLedger` slot key; `request_id` is an added parallel field).
- **Cannot do.** Doesn't make two **simultaneous** utterances distinguishable at the audio layer (the ceiling).
- **Risks.** v1 `request_id==turn_id` invites "why add it?" (answer: durable cross-turn handle) — be explicit;
  orphaned inline entry left `running` if the reply handle is lost (settle in the `TurnLedger.close()` sweep);
  threading the id through the stdlib-only terminal emitter (keep it stdlib-only).

### P3 — Conversation/intent threads (Slack-thread model)

- **Thesis.** Model the meeting as concurrent **threads of intent** (each = one ask + its decisions + deliveries +
  background work, lifecycle `open→active→paused→resolved/abandoned`); a **`thread_id`** is the durable key all
  execution attaches to; render three **thread-faceted lanes** that filter/link by thread.
- **Correlation.** Two keys, layered, never conflated: `turn_id` (per-utterance INV-1) + new `thread_id`
  (grouping). Thread assignment is a **deterministic** coreference resolver (keyword/kind + deictic + recency),
  **not an LLM call**, and **observability-only** — a misgroup is a cosmetic lane error, never a wrong answer.
- **Task model.** Same inline→first-class-task unification, behind `AgentTask` + `TaskCoordinator`.
- **Proactive delivery.** Reuse `TaskSpeechDeliverer`/`SpeechQueue` verbatim; add delivery↔thread correlation.
- **Phases.** Phase 0 thread spine *(L, no behaviour change)* → Phase 1 coreference resolver *(M)* → Phase 2 unify
  inline work *(L)* → Phase 3 Panel C + thread lanes *(L, `Johnny-trt.33`)* → Phase 4 proactive delivery↔thread *(M)*.
- **INV-1/INV-2.** Untouched (`thread_id` is a grouping on top of `turn_id`).
- **Cannot do.** Can't make the small router's intent detection reliable; genuinely ambiguous "that/it" across
  multiple open **same-kind** threads may mis-attach (degrades to one-thread-per-turn).
- **Risks.** Coreference is the hard part (mitigated by determinism + observability-only + graceful degrade);
  continue-vs-new-thread on barge-in (RULE: only a *fresh kind not in any open thread* opens a new thread, reusing
  the `occupied_kinds` mechanism the router already trusts).

### P4 — Background-task actors + delivery arbiter/inbox

- **Thesis.** Promote **every** non-trivial unit of work (including the inline 43 s loop) into a first-class
  **task actor** that runs in parallel, streams rich progress, and posts its result to a **delivery inbox** an
  **arbiter** (the shipped `SpeechQueue`/`Deliverer`) speaks back at a conversational boundary; the three panels are
  projections of that one task model.
- **Correlation.** Minimal `request_id = f"{session_id}:{turn_int}:{seq}"` minted at gate entry and propagated via
  a **contextvar**; explicitly depends on P1/P2 for richer semantics.
- **Task model.** The full unification — inline and delegated both become task actors on the `AgentTaskStatus`
  machine.
- **Proactive delivery.** Two regimes: **regime 1** (turn-inline, fast — the reply *is* the answer) and **regime 2**
  (result outlives its turn → inbox → arbiter boundary delivery). Machinery already exists.
- **Phases.** P4.0 correlation foundation *(M, depends P1/P2)* → P4.1 inline loop → task actor *(L, the split-brain
  fix)* → P4.2 inline progress + interruption state *(M)* → P4.3 inline result → delivery inbox (proactive) *(M)* →
  P4.4 Panel C tasks stream *(L, `Johnny-trt.33`)* → P4.5 Panels A/B + 3-lane board *(L)* → P4.6 docs +
  replay-harness adaptation *(S)*.
- **INV-1/INV-2.** Unchanged and explicitly protected (task actors never emit a `TurnTerminal`).
- **Cannot do.** No true multi-utterance parallel routing (the await-chained ceiling).
- **Risks.** Hard dependency on P1/P2 for `request_id`; **contextvar propagation through the LiveKit-owned tool
  loop is the load-bearing assumption** (verify with a smoke test that an MCP call inside `llm_node` sees the
  contextvar; fallback: stash on `AgentSession` userdata); double-delivery if an inline result is both spoken as
  the reply *and* enqueued (mark delivered atomically; reuse the `trt.29` `mark_result_delivered` seam).

## 3. Adversarial judge panel (3 independent lenses)

Three judges scored all four proposals on five axes (1–5, max 25): **product** (does it dissolve the session-3
pain?), **staff-eng** (soundness/migration safety/invariants), **shipping** (incremental, reversible, reuse).

| Proposal | Product | Staff-eng | Shipping | **Avg** |
|---|:--:|:--:|:--:|:--:|
| **P1 — Incremental UI-first** | 23 | 23 | 24 | **23.3** 🥇 |
| **P2 — `request_id` backbone** | 19 | 22 | 21 | **20.7** 🥈 |
| **P3 — Conversation threads** | 18 | 17 | 17 | **17.3** |
| **P4 — Task-actor + arbiter** | 18 | 18 | 15 | **17.0** |

**Top picks:** P1 (product + shipping judges), P2 (staff-eng judge). **All three judges independently recommended
the same ordering:** ship **P1 now → P2 backbone → P4 delivery as a behavioural capstone → Threads as an optional
UI skin last.** When three separately-reasoning panels converge on one sequence, that sequence is the answer.

**Axis pattern.** P1 swept incrementality/reuse/effort (straight 5s) — it's the only plan that dissolves the felt
pain *this phase* with near-zero risk. P2 swept technical soundness (5/5/5) and is the "correct" durable
foundation, but costs incrementality. P3 has the **highest intent-fidelity** (the "juggle like a person" UX) but
the **lowest** soundness/incrementality (it bets the spine on coreference over an already-fragile small router).
P4 reuses the shipped delivery machinery but hard-depends on P1/P2 to define `request_id`, so it literally cannot
go first.

**Code-level corrections the panel surfaced (verified against the source — these sharpen the parallel agent's PRD/DESIGN):**

- **`agent_model_calls` has no `agent_task_id` column** (`models.py:1136` — only `turn_id`/`role`/`step_index`). So
  "set `agent_task_id` on the model-call writer" is **false without a migration**. Phases 1–2 group model calls by
  `turn_id` (1:1 with the per-turn work_unit); the column is added later under the `request_id` migration.
- **The tool-call trace sink fixes `agent_task_id` at construction** (`agent_tasks.py:210`) while `turn_id` is
  per-call — add a **per-call `resolve_agent_task_id`** so inline tools hang off the work_unit, not the
  timestamp-orphan net.
- **Cross-thread bleed has a precise root cause:** `_on_reply_done_inner`'s caption `take()` can stamp a **stale
  partial onto `final_text`** — fix by request/turn-scoping the single `SpeechCaptionBuffer` at the `AgentSpoke`
  kind boundary (this is the backend correctness fix the RED-TEAM flagged).
- **The gate serializes one turn at a time** (`_active_reply` is a single binding) — confirming the §0 ceiling:
  `request_id` correlates *downstream streams* and lets *results* run/deliver in parallel, but **triage stays
  sequential**; making the gate itself concurrent is a much larger, separate change.
- **Use the proven `_resolve_speech_turn` seam for `request_id`**, *not* P4's contextvar-through-the-LiveKit-loop
  bet (the codebase does not propagate contextvars through the tool loop today — unverified assumption).

➡️ **The full code-verified recommendation** — exact seams (`begin_inline`/`settle_inline`, the `_on_reply_done`
wiring, the trace-sink resolver, worker `exclude_kinds`), the 5-phase roadmap with bd mapping, the migration, and
the INV-1/INV-2/replay-harness analysis — is in **[`SYNTHESIS-RECOMMENDATION.md`](./SYNTHESIS-RECOMMENDATION.md)**.

## 4. Recommended synthesis — they stack, so phase them

The four options are **not** a pick-one menu; they are **increasing radii** around the same center. The
recommended path climbs the stack, shipping operator-visible value at each rung and stopping wherever the operator's
appetite (see `RED-TEAM-REVIEW.md` §7) lands:

- **Rung 1 — P1 P0/P1 (ship first, low risk).** Split the UI into the three panels over existing data + wire the
  dropped `task_*` events + make the inline loop a `work_unit` task. **Closes `Johnny-trt.33`** and *immediately*
  fixes "no tasks in flight" in session-3-style cases. No schema migration.
- **Rung 2 — P2 (correlation backbone).** Add the durable `request_id` and attribute deliveries + inline work to
  their request. This is the addition the DESIGN.md correctly called *"the highest-value single addition,"* and it
  is what makes **View 2's "which request"** real across turns.
- **Rung 3 — choose the spine:** **P3 threads** (if the operator wants the "juggling like a person" lanes UX and
  cross-turn intent grouping) layered on the `request_id`; and/or **P4 task-actor + arbiter** (if the operator wants
  the bot to **move heavy work off-turn** and **proactively report back**). P4 is what actually **un-blocks the
  turn** — the behaviour change the RED-TEAM argues is necessary, not optional, to dissolve the operator's felt
  pain. P3 and P4 compose (threads group; actors execute + deliver).

This phasing is consistent with the parallel agent's "B delivered in phases that start with A" framing — it just
makes the **rungs**, the **stacking**, and the **off-turn behaviour decision** explicit, and it keeps each rung
independently shippable and reversible.

**Relationship to the parallel agent's data model:** Rung 2's `request_id` is the *correlation* half; the
unified-work-unit (whether realized as the PRD's new `agent_workstreams` entity or as P1's `work_unit` on
`agent_tasks` + a `source_kind`) is the *execution* half. Per `RED-TEAM-REVIEW.md` §2, adopt **both**, and prefer
evolving `agent_tasks` + `source_kind` over a parallel `agent_workstreams` table unless a concrete need forces the
new entity (smaller blast radius, reuses the worker/registry/speech-queue contracts verbatim).

## 5. How the options answer the operator's open decisions

| Operator decision (RED-TEAM §7 / PRD §14 / DESIGN §10) | What the options say |
|---|---|
| Observability **or** behaviour change? | Rungs 1–2 = observability + correlation; **Rung 3 (P4)** = behaviour (off-turn work + proactive delivery). The felt pain needs at least opt-in P4. |
| One correlation id or two (request vs work)? | Two, orthogonal: `request_id` (correlation) **+** unified work-unit (execution). Don't let one stand in for the other. |
| Request = one turn or cross-turn intent? | P2 = durable cross-turn handle; P3 = full intent threads if you want the lanes UX. |
| Proactive vs on-demand delivery? | Machinery exists (`TaskSpeechDeliverer`, boundary-gated). P4 makes it first-class; default proactive-when-floor-free, on-demand always available. |
| New table or evolve `agent_tasks`? | Prefer evolve + `source_kind` (P1/P2/P3 path); reserve a new entity for a proven need. |
| Replay determinism of promotion? | Gate inline-task creation on **deterministic, persisted** signals (tool-step seen / router action), not timing/LLM-text — keeps the replay harness green. |
